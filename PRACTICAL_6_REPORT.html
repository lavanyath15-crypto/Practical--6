1. Aim

To develop a RESTful API using Node.js and Express.js connected to a database, implement complete Create, Read, Update, and Delete (CRUD) operations, deploy the application on a cloud web hosting platform, and verify all API endpoints using Postman.

2. Objectives

  • To design and build a RESTful API using Node.js and Express.js adhering to standard HTTP methods.
  • To connect the application to a MongoDB database using Mongoose ODM with schema validation constraints.
  • To implement complete CRUD operations:
    • Create new student records using POST.
    • Retrieve all or individual student records using GET.
    • Update existing student records using PUT.
    • Delete student records from the database using DELETE.
  • To test and verify all API endpoints locally and in production using Postman.
  • To deploy the application to a web hosting provider (Render) and make it accessible through a public URL.

3. Problem Statement

Student registration and record management systems require accurate, persistent data handling from users and client applications. Direct database access from client applications introduces security vulnerabilities, lack of validation, and tight coupling.

The Student Records RESTful API Management System provides an independent, scalable back-end web service that validates user input, prevents duplicate roll numbers and emails, performs database CRUD operations, and returns standardized HTTP status codes and JSON responses.

4. Technologies Used

  • Node.js: Asynchronous, event-driven JavaScript runtime environment for executing back-end logic.
  • Express.js: Fast, unopinionated minimalist web framework used for routing, middleware, and request/response handling.
  • MongoDB & Mongoose: Document-based NoSQL database and Object Data Modeling (ODM) library providing schema structure, field validation, and query execution.
  • Postman: API testing and documentation platform used to design and execute automated HTTP requests.
  • VS Code: Integrated Development Environment used for coding, debugging, and terminal operations.
  • Git and GitHub: Manage and host the project source code with version control.
  • Render: Cloud web hosting provider used to deploy the web service with environment variables.

5. System Implementation

5.1 RESTful API Architecture & Endpoints

The system adheres to standard REST architecture, using stateless HTTP communication and returning structured JSON payloads.

Method Endpoint Description Status Code
GET /api/health Service health and MongoDB connection status 200 OK
POST /api/students Create a new student record in database 201 Created / 400 / 409
GET /api/students Retrieve all student records from database 200 OK
GET /api/students/:id Retrieve a single student by ObjectId or Roll Number 200 OK / 404 Not Found
PUT /api/students/:id Update an existing student record 200 OK / 400 / 404
DELETE /api/students/:id Delete a student record from database 200 OK / 404 Not Found

5.2 Database Model & Validation

The student entity is defined in models/Student.js using Mongoose Schema with strict validation constraints:

  • name: Required string, trimmed.
  • rollNo: Required uppercase string, unique index to avoid duplication.
  • email: Required lowercase string, validated via regular expression, unique index.
  • course: Department/major with default value.
  • gpa: Number constrained between 0.0 and 10.0.

5.3 Controller Logic & CRUD Operations

The application logic is partitioned into dedicated controller functions in controllers/studentController.js:

  • createStudent: Validates payload attributes, checks existing records for duplicate roll number or email (returning 409 Conflict), and creates the record returning 201 Created.
  • getAllStudents: Fetches all student documents from the database, supporting optional search and filtering queries.
  • getStudentById: Performs lookup by either 24-character hexadecimal MongoDB ObjectId or roll number.
  • updateStudent: Modifies existing student details with validator enforcement.
  • deleteStudent: Removes the document from the database and confirms deletion.

5.4 Application Structure and Code Organisation

The project follows the Model-View-Controller (MVC) pattern, separating routing, business logic, data models, and static views.
